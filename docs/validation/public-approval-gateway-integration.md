`createLocalGateway` installs this same bridge for `sopStatus` and all human `resumeSop` RPC calls. Only server-authenticated subject and resolved session information reach the original control/store. External-task resume retains its original source path and receives a whitelist of existing command fields; caller authority is rejected and the original store refuses external-task source for a human wait. The stable selected profile/store remains unchanged. Human first use and replay reauthenticate; there is no pending-wait GET preflight, and the original resumeRequests receipt decides duplicate/revision under its lock.

The existing Gateway HTTP server now registers these exact POST endpoints:

- `/api/module-host/approvals/status`: body `{tenantId,agentId,sessionKey,projectKey?}`, response `{status:<original snapshot|null>}`. Snapshot contains the owner's pinned `approval` or explicit `approvalError`.
- `/api/module-host/approvals/resume`: same scope plus `{source:'human',requestId,waitId,expectedRevision,message,slotUpdates?}`, response is the original resume receipt.

Both require the existing Gateway `Authorization: Bearer <normal service token>` and a separate `X-StaffDeck-Approver-Authorization: Bearer <approver SD login token>`. Unexpected fields, caller authority, other scope, missing credentials and missing/foreign authoritative mapping cannot submit. A64KiB body limit and request disconnect signal apply. Approval credentials never enter persistent state or returned receipts; the original domain stores only authorization facts in its existing resumeRequests.

The original PD `/api/sop/status` and human `/api/sop/resume` are still under PD authenticateToken. They additionally check the configured PD user binding and convey the independent SD approver header via the original RPC. Root authenticates again; body.authority is never forwarded. SOP RPC errors preserve original authentication HTTP status through `details.httpStatus`; the HTTP consumer uses that status, not a code-only401 approximation.
